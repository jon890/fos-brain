# planning — 구현 전 8단계 설계

구현에 들어가기 전 모호함을 모두 없애고 의사결정을 docs 로 산출하는 설계 워크플로우.
새 프로젝트에 하네스를 깔 때 이 페이지를 seed 로 꺼내 `planning` 스킬을 재구성한다.
8단계를 마치면 task 파일이 만들어지고, 실제 구현은 `build-with-teams` 로 넘어간다.

## 핵심 철학

- 속도와 안정성 트레이드오프 — 빠른 MVP 를 출시하되 안정적으로 만든다.
- 모호함 제로 — 각 단계에서 조금이라도 모호하면 반드시 사용자와 논의하고, 넘어가지 않는다.
- AI 에이전트 관점 — 최종 문서는 에이전트가 읽고 바로 구현할 수 있을 만큼 명확해야 한다.
- 간결한 문서 — 의사결정 의도는 보존하되 구현 상세는 코드에 둔다.
- 선택지는 1클릭 인터랙티브로 — 긴 글로 옵션을 나열하면 사용자 답변 부담이 크다.

## 8단계 골격

각 단계는 사용자 확인을 거쳐 다음으로 넘어간다.
규모가 작으면 단계를 합치거나 생략한다.

0. 업무 매핑 — 이 작업이 어느 이슈·업무에 속하는지 먼저 확정한다. 매핑 없이 진입 금지.
1. 구현 가능성 검증 (CTO 역할) — 기술 가능성, 재사용 가능한 기존 코드, 리스크·제약.
2. 기술 스택 검증 — 기존 스택으로 충분한지. 새 의존성은 추가 위치·버전 핀·대안을 논의.
3. API 호출 흐름 검증 (API 디자이너 역할) — 요청부터 응답까지 시퀀스, 외부 의존성, 엣지 케이스.
4. 응답·에러 모델 설계 — DTO 필드 (옵셔널·필수), 에러 코드 매핑, HTTP status 정책.
5. API 설계 — 엔드포인트 목록, 요청·응답 모델 초안, async 흐름 결정.
6. 데이터·아키텍처 설계 (CTO 역할) — 스키마 변경, 디렉터리·레이어, 기존 패턴 일관성.
7. 기술 결정 점검 — 이번에 내린 결정을 목록화하고 각 "왜" 를 기록한다.
8. 최종 문서 생성 — ADR 자명성 게이트를 통과한 결정만 docs 에 반영하고 task 를 만든다.

## 규모별 단계 스킵

| 규모 | 권장 단계 |
|---|---|
| 소 (버그 수정, 옵션 한 줄 변경) | 1 → 8 |
| 중 (엔드포인트 확장, 옵션 추가) | 1 → 5 → 6 → 7 → 8 |
| 대 (신규 엔드포인트, 구조 변경, 새 의존성) | 전체 8단계 |

## ADR 자명성 게이트 (8단계의 핵심 결정 규칙)

기술 결정을 ADR 로 남길지 거르는 관문이다.
아래 3질문에 **모두 NO** 여야 ADR 로 기록한다.
하나라도 YES 면 코드 주석·커밋 메시지·다른 규칙 문서로 내려보낸다.

1. 설정 파일·디렉터리 트리·기존 docs 중 하나를 보면 같은 정보를 얻는가?
2. "왜 X 를 선택했다" 를 1~2문장 이상으로 설명하기 어려운가?
3. 다른 프로젝트에서도 일반적으로 하는 선택인가?

ADR 유지 적격 유형:

- 라이브러리 고유 함정 (문서에 없거나 직관에 반하는 API 특성)
- 실험 결과 (A/B 비교·수치 근거)
- 대안 기각 근거 (미래에 재논의될 여지)
- 정책·규칙 (팀 합의로 정한 규율)
- 비용·성능 트레이드오프 (수치 있는 결정)

ADR 본문은 "결정 / 맥락 / 대안 기각" 3축을 모두 채운다.
한 축이라도 비면 적격성을 다시 본다.
자명성 판정의 상세 기준은 [[docs-six-axis-audit]] 의 E 축과 같은 원칙이다.

## 의사결정 즉시 docs 반영

8단계를 기다리지 않는다.
각 단계에서 결정이 나면 그 즉시 해당 문서에 반영한다.
논의가 길어질 때 결정이 유실되는 것을 막고, 다음 대화에서도 맥락을 참조하게 한다.
이 규율이 [[docs-first-adr]] 의 "task 생성 전 docs commit" 과 맞물린다.

## phase = 코드 작업 only

planning 이 만드는 task 의 phase 는 로컬에서 완결되는 코드 작업만 담는다.

- phase 가 다루는 것 — 코드 변경, 로컬 검증 (import smoke / unit test / 로컬 서버 호출), docs 갱신.
- phase 가 다루지 않는 것 — 운영 배포, 메트릭·대시보드 확인, 릴리스 태그, 사용자가 직접 트리거하는 워크플로.
- self-check — phase 본문에 배포·운영 키워드 (CI 빌드, 배포 콘솔, 대시보드, 릴리스 태그) 가 보이면 별도 흐름으로 분리한다.

배포·운영 흐름은 release 계열 스킬의 책임이다 (NHN 환경 사례는 비공개 노트로 분리).

## 문서 단일 소스 + 변경 영향 표

같은 정보를 두 문서에 본문으로 쓰지 않는다 — 정의는 1곳, 나머지는 링크·짧은 참조.
변경 유형별 "docs 영향 표" 를 둬서 "이 변경이면 어떤 docs 를 손대는가" 를 명시하면 누락이 0 에 수렴한다.
이 표가 단일 소스이므로, 같은 식별자가 docs 와 코드 양쪽에 정의되는 경우 (메트릭 이름·응답 필드·환경변수 등) plan 단계에서 양쪽 표기를 한 번에 결정한다.

## PR 시점

PR 은 plan 단계에서 만들지 않는다.
설계 commit 만으로는 변경 의도가 절반밖에 표현되지 않아 리뷰 가치가 낮다.
구현 phase commit 들이 같은 브랜치에 쌓인 뒤 한 PR 로 묶어야 리뷰·머지·롤백 단위가 깔끔하다.
