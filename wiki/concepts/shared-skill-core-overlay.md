# 공용 스킬 코어와 레포 오버레이

여러 레포에 복제된 Claude Code 스킬을 **단일 코어와 레포별 오버레이**로 나눠, 개선을 한 곳에서만 하고 전 레포에 반영하는 배포 구조.

## 문제

같은 스킬(예: `planning`)을 여러 레포에 복사해 두면, 스킬을 하나 고칠 때마다 N개 레포에 손으로 다시 이식해야 한다. 시간이 지나면 레포마다 미묘하게 갈라져(divergence) 유지비가 계속 쌓인다. [[ai-harness-pattern]] 을 여러 프로젝트에 퍼뜨릴수록 이 비용이 커진다.

## 구조

- **코어** (단일 소스): 도메인 중립 워크플로만 담는다 — 단계 뼈대, 핵심 원칙, 공용 검증기. 전용 레포(예 `fos-skills`)에 두고 글로벌 `~/.claude/skills/<name>` 로 symlink 해 모든 프로젝트에서 쓴다.
- **오버레이** (레포별, 작게): 그 레포만의 특화를 담는다 — 도메인 단계 변형, docs 컨벤션, 검증 경로, 실행 핸드오프 명령. 각 레포 `.claude/<skill>-overlay.md`.
- 코어가 시작 시 현재 레포의 오버레이를 읽어 뼈대를 채운다. 오버레이가 없으면 코어 기본값(도메인 중립)으로 동작한다.

오버레이는 코어를 *덮어쓰는* 게 아니라 *채운다* — 코어가 뼈대이고 오버레이가 살점을 붙인다.

## 효과

- 워크플로 개선 = 코어 1곳 수정 → 전 레포 즉시 반영. 수동 포팅이 사라진다.
- 각 레포의 거대 스킬 파일이 얇은 오버레이로 줄어든다.

## 함정

- **전역 override 주의**: 전용 레포를 글로벌 `~/.claude/skills` symlink 로 노출하면, Claude Code 우선순위상 개인 전역이 프로젝트 스킬을 이긴다(personal > project). 자체 in-repo 동명 스킬을 가진 다른 레포가 그 머신에서 가려진다. 개인 단독 레포 묶음엔 적합하나 팀 공용(자체 in-repo 스킬 유지) 레포엔 부적합하다.
- 통째 복사가 아니라 레포별로 특화만 추출해야 한다 — 통짜 이식은 각 레포 특화를 날린다.
- 스킬을 코어로 옮길 때 의존 스킬의 하드코딩 경로나 삭제 대상 하위의 공유 자원이 함께 깨질 수 있다. 삭제 전에 참조를 전수 grep 하고 공유 자원을 중립 위치로 먼저 옮긴다.

기획·구현 스킬의 배포와 유지보수 진화형이다. [[script-skill-separation]]이 한 스킬 내부의 실행과 문맥 분리라면, 이 방식은 여러 저장소에 걸친 스킬 공유 구조다.
