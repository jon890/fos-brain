# GraphRAG 경로 검색

GraphRAG 검색은 그래프 전체를 펼치는 일이 아니라 질문에 맞는 시작 노드와 관계 경로를 남겨 설명 가능한 서브그래프를 만드는 일이다.

## 검색 흐름

1. 텍스트·벡터 검색으로 질문과 관련된 시작 노드 후보를 찾는다.
2. 관계를 확장할 때마다 경로에 점수를 매긴다.
3. 상위 경로만 다음 깊이로 넘기는 beam search 방식으로 폭발을 제한한다.
4. 제품별 path preference로 선호하는 노드와 관계에 가중치를 준다.
5. 결과와 함께 어떤 노드와 관계를 따라갔는지 반환한다.

## 좋은 경로를 남기는 기준

- 질문에서 찾은 시작 노드가 경로에 다시 나타나면 관련성 근거로 활용할 수 있다.
- 최신성, 중요도와 제품 목적은 도메인별 점수 함수로 분리한다.
- 시작 노드가 틀리면 이후 탐색 전체가 흔들리므로 시작점 검색을 별도로 평가한다.
- 경로 수, 탐색 깊이와 단계별 생존 수를 제한해 메모리와 지연 시간을 통제한다.

## 그래프 저장소 운영

- 인덱스를 적용할 시작 노드를 먼저 좁힌다.
- 관계 방향과 타입 조건을 탐색 초기에 적용한다.
- 각 확장 단계에서 정렬과 제한을 적용한다.
- 실행 계획으로 행 증가와 메모리 할당 지점을 확인한다.

## 추가 (2026-08-27)

발표 영상의 글 판본에서 자동자막이 뭉갠 수치와 파라미터 이름을 확인했다.

### 경로 폭발은 홉 하나마다 자릿수가 바뀐다

지식 그래프 한 노드에서 출발한 후보 경로 수의 실측 사례다.

| 홉 | 후보 경로 수 |
| --- | --- |
| 1홉 | 1,105건 |
| 2홉 | 134,520건 |
| 3홉 | 49,241,786건 |

의미 있는 서브그래프를 만들려면 3홉 이상이 필요한데, 그 지점의 후보를 모두 메모리에 두고 점수화하고 정렬하는 작업은 그래프DB의 트랜잭션 메모리로 감당하지 못한다.
그래서 실제 문제는 얼마나 깊이 갈지가 아니라 각 홉에서 무엇을 일찍 버릴지다.

beam search로 홉마다 상위 후보만 남기면 깊이를 확보할 수 있지만, 일찍 제외한 경로는 되살아나지 않는다.
탐색 제한을 도입한 다음 과제는 항상 점수 함수 설계로 넘어간다.

### 도메인 신호는 주 신호가 아니라 보조 신호로 둔다

시가총액과 최신성은 순위를 결정하는 값이 아니라, 질문 관련도가 비슷한 후보들 사이에서 순서를 가르는 값이다.
이 경계를 흐리면 질문과 무관한 대형 종목이 상단을 차지한다.

### 탐색 의도는 검색기를 복제하지 말고 파라미터로 받는다

제품마다 보고 싶은 관계의 흐름이 다를 때, 특정 노드 유형의 순서와 일치하는 경로에 가산점을 주는 파라미터를 둔다(사례의 이름은 `path_preference`).
관련 없는 경로를 완전히 제외하는 대신 선호 경로가 탐색 과정에서 더 오래 살아남게 한다.
덕분에 같은 그래프 위에서 검색기를 하나만 유지하면서 제품별 의도를 반영할 수 있다.

### Cypher는 실행계획을 직접 확인해야 한다

그래프 탐색은 시작 노드와 관계 분포에 따라 중간 후보 수가 크게 달라지므로 쿼리 플래너에만 기댈 수 없다.

- 노드 라벨과 인덱스가 걸린 속성을 함께 명시하고 실행계획에서 인덱스 탐색이 쓰이는지 확인한다.
- 관계 방향과 타입, 노드 필터를 확장 초기에 적용한다.
- 다음 단계에 필요한 값만 넘겨 큰 중간 결과가 쿼리 안에 오래 남지 않게 한다.
- 예상 계획을 먼저 보고, 대표 파라미터로 실제 비용을 측정한다.
- 측정에서는 예상 행 수와 실제 행 수의 차이, 관계 확장 지점의 조회 횟수, 연산자별 메모리 사용량을 본다.

Cypher 최적화의 핵심은 후보가 어느 지점에서 늘어나는지 찾아 다음 탐색 전에 줄이는 것이다.
