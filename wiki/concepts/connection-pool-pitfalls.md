# 커넥션 풀 4대 함정

공식대로 풀 사이즈를 잡아도 터지는 실무 함정 넷. 대부분의 풀 고갈은 풀 크기 문제가 아니라 커넥션 점유 시간 문제다.

## 1. 롱 트랜잭션 (가장 흔한 원인)

- 트랜잭션 안에서 외부 API 호출·무거운 계산을 하면 커넥션 점유 시간이 길어져 풀이 고갈된다.
- 공식에 맞게 잡아도 긴 트랜잭션 하나가 풀을 말린다.
- 회피 — 트랜잭션을 최대한 짧게 하고, 외부 호출은 트랜잭션 밖으로 뺀다.

## 2. maxLifetime vs DB idle timeout 미스매치

- HikariCP maxLifetime(기본 30분)이 DB 또는 중간 계층의 idle timeout 보다 길면, DB 가 먼저 끊은 커넥션을 풀이 모르고 쥐고 있다가 쓸 때 오류가 난다.
- PostgreSQL idle timeout 은 기본 무제한, MySQL 은 8시간이라 직접 연결은 보통 문제가 없다.
- 실무에서 터지는 건 중간 계층 때문이다 — PgBouncer(기본 10분)·RDS Proxy·NLB 가 더 짧은 타임아웃을 건다.
- 회피 — maxLifetime 을 DB·인프라 타임아웃보다 30초 이상 짧게 둔다.

## 3. CM>1 — 한 스레드가 여러 커넥션 점유

- 한 요청이 커넥션을 여러 개 동시에 잡는 코드(중첩 트랜잭션)는 데드락 위험이 있다.
- 데드락 회피 최소 공식은 `풀 = 스레드 수 × (스레드당 동시 커넥션 − 1) + 1`(HikariCP)다. 단 대부분 앱은 스레드당 1커넥션이라 무의미하므로, 데드락이 났을 때의 진단용으로 본다.
- 회피 — 풀을 키우기보다 코드 구조를 고친다(트랜잭션 분리).

## 4. 커넥션 누수

- 빌린 커넥션을 반납하지 않으면 풀이 마른다.
- HikariCP leakDetectionThreshold(예: 60초)를 설정하면 그 시간 넘게 미반납인 커넥션을 로그로 경고한다.
