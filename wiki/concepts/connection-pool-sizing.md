# DB 커넥션 풀 사이징

DB 커넥션 풀의 최대 크기를 결정하는 공식과 진단법. 핵심은 "많을수록 좋다"가 아니라 CPU 처리 능력에 맞춘 작은 값에서 시작해 부하 테스트로 조정하는 것이다.

## 시작 공식

- `풀 사이즈 = 물리 코어 수 × 2 + 유효 스핀들 수` (PostgreSQL 위키 경험칙)
  - 물리 코어만 센다 — 하이퍼스레딩 논리 코어는 제외한다(DB 작업은 캐시 미스가 잦아 효과가 적다).
  - 스핀들은 HDD 회전축 수다. SSD·NVMe·메모리 캐시 환경에서는 0이다.
  - 2026 현실에서는 사실상 `물리 코어 × 2`다.
- 이 값은 시작점일 뿐이다 — 부하 테스트로 sweet spot 을 찾는다.
- 라이브러리 기본값 — HikariCP 10, node-postgres 10, SQLAlchemy 5+10. .NET 은 100이지만 상한이지 권장값이 아니다.

## 많을수록 느려지는 역설 (USL)

보편적 확장성 법칙(Universal Scalability Law) — 동시 처리 단위를 늘리면 자원 경쟁과 일관성 비용이 누적되어 어느 지점부터 처리량이 평탄화·하락한다.

- 컨텍스트 스위칭 — 코어보다 많은 스레드는 교체에만 시간을 쓰고 CPU 캐시를 무효화한다.
- 락 경쟁 — 같은 행을 노리는 커넥션이 많을수록 대기 시간이 길어진다.
- 캐시 효율 저하 — 많은 커넥션이 서로 다른 데이터를 읽어 버퍼 캐시가 빠르게 교체된다.

핵심은 동시에 일하는 커넥션이 CPU 처리 능력만큼만 의미가 있다는 점이다. 이 원리는 스레드 풀·HTTP 클라이언트 풀 등 모든 풀에 적용된다. 처리량이 더 늘지 않는 지점이 시스템의 한계점(saturation point)이다.

## Little's Law 진단

- `TPS = 활성 커넥션 수 / 쿼리 실행 시간` (리틀의 법칙)
- 풀 크기를 정하는 공식이 아니라 풀 부족과 쿼리 부족을 구별하는 진단 도구다.
- 활성 커넥션이 `코어 × 2` 에 도달했으면 풀을 늘려도 처리량이 늘지 않는다 → 쿼리 응답 시간을 줄인다(인덱스·캐시·튜닝).
- 코어에 여력이 있으면 그때 풀 확장을 검토한다.

## WAS 다중 인스턴스 분배

- WAS 가 여러 대면 WAS별 풀을 곱하면 안 된다 — 합산이 DB 용량을 초과한다.
- 분배 시작점은 `(코어 × 2) / WAS 수` 다.
- 트레이드오프가 갈린다.
  - DB 보호 우선 — 정확히 나눠 합계를 `코어 × 2` 이내로 둔다.
  - 가용성 우선 — 약간 여유를 둬 한 대가 죽어도 나머지가 부담을 견디게 한다.
- 오토스케일링 환경은 PgBouncer 같은 외부 풀러를 쓴다.

## DB max_connections 한계

- 모든 WAS 풀 사이즈의 합이 DB 의 max_connections 를 넘으면 장애가 난다.
- 가용 커넥션은 `(max_connections − 시스템·관리자 예약) × 0.8` 정도로 본다.
- PostgreSQL 기본 max_connections 는 100이고, 프로세스 기반이라 커넥션당 수~수십 MB 를 잡아먹는다.
- 초과가 필요하면 max_connections 를 올리기보다 PgBouncer 외부 풀러를 둔다.

## 운영 황금률

- 잘 도는 시스템은 건들지 않는다 — 측정이 먼저다.
- 피크 시간 평균 활성 커넥션을 풀 사이즈로 나눈 비율로 판단한다 — 25% 이하면 축소가 안전하고, 60% 이상이면 축소하지 않는다.
- 풀 축소는 확장보다 위험하다(트래픽 폭증 시 즉각 장애). 단계적으로 적용하고 롤백 가능하게 준비한다.
