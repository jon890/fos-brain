# ADR 005: Brain 근거 질문을 같은 출처 중계 계층으로 제한한다

## 상태

승인

## 배경

Memory Atlas에서 개인 brain을 직접 질문하고 답변 근거 문서로 이동할 수 있어야 한다.
보호 사이트에는 public과 private wiki가 함께 있으므로 질문 경로도 같은 Cloudflare Access 경계를 따라야 한다.

qmd HTTP는 인증이 없고 검색 발췌문만 반환한다.
Hermes API는 terminal과 파일 도구를 포함한 강한 권한을 가질 수 있으며 API key를 요구한다.
브라우저가 두 서비스를 직접 호출하면 key와 내부 주소가 노출되고, 근거 경로와 입력 크기를 서버에서 통제할 수 없다.

기존 `career-api`는 여러 외부 skill과 도구가 활성화된 다른 목적의 프로필이다.
brain 질문은 읽기 전용 문서 근거만 필요하므로 이 권한을 재사용하면 경계가 지나치게 넓어진다.

## 결정

`brain-web`과 내부 서비스 사이에 Node.js 24 기반 `brain-ask`를 둔다.
브라우저는 같은 출처의 `POST /api/brain/ask`만 호출한다.
`brain-ask`는 `brain-wiki`와 `brain-private`를 검색하고 검증한 wiki 본문만 읽어 Hermes에 전달한다.

Hermes에는 전용 `brain-api` 프로필을 만든다.
이 프로필은 `brain` 모델 별칭만 제공하고 모든 toolset과 외부 skill 경로를 끈다.
요청마다 `store: false`를 사용하고 대화나 질문·답변 기록을 남기지 않는다.

첫 버전은 한 번에 한 질문만 처리한다.
최대 6개 문서와 32 KiB 근거를 사용하고, 근거가 없으면 Hermes를 호출하지 않는다.
답변 출처는 모델 출력이 아니라 qmd 검색 결과로 서버가 만든다.

`brain-ask`, qmd와 Hermes는 호스트 포트를 열지 않는다.
Hermes API key는 mode 600 파일로만 전달하며 브라우저, git과 container 환경 변수에 넣지 않는다.

새 프로필과 질문 경로의 실서버 검사가 통과한 뒤 기존 `career-api`와 127.0.0.1:8643 연결을 제거한다.

## 결과

- Cloudflare Access가 사람 인증을 계속 담당하고 API에 별도 로그인 화면을 만들지 않는다.
- 브라우저에서 Hermes key와 내부 qmd 주소를 볼 수 없다.
- 질문 입력, 근거 크기, 파일 경로와 응답 형태를 한 곳에서 검증할 수 있다.
- Hermes가 검색이나 파일 도구를 임의로 호출하지 못한다.
- 답변 생성 장애와 정적 wiki 탐색 장애를 분리할 수 있다.
- `brain-ask`와 전용 프로필을 배포하고 운영하는 비용이 추가된다.
- 첫 버전은 스트리밍, 대화 이력과 동시 질문을 지원하지 않는다.

## 검토한 대안

### 브라우저에서 Hermes를 직접 호출한다

API key와 내부 서비스가 노출되고 입력·응답 경계를 통제하기 어려워 제외했다.

### 기존 `career-api`를 재사용한다

사용 목적이 다르고 외부 skill과 강한 도구 권한이 남아 있어 최소 권한 원칙에 맞지 않는다.

### Hermes 도구가 qmd를 직접 검색한다

검색 결과와 읽은 파일을 결정적으로 제한하기 어렵고 불필요한 도구 권한이 생겨 제외했다.

### 모델 제공자 API를 직접 사용한다

현재 홈서버의 Hermes 모델 설정과 인증을 중복 관리하게 되어 제외했다.

### 첫 버전부터 스트리밍과 여러 차례 대화를 지원한다

연결 복구, 기록 수명과 사용자별 상태 계약이 필요하다.
읽기 전용 단일 질문의 품질과 보안 경계를 먼저 검증하기 위해 다음 단계로 미뤘다.
