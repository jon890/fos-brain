# 지식 저장·검색·탐색 흐름

## 저장 흐름

1. `brain-add`나 `brain-curate`가 소스를 임시 위치에서 읽고 지식 후보를 만든다.
2. 각 후보가 6개월 뒤 답할 질문, 개인적 특수성, 적절한 단일 소스, 출처, 공개 범위를 갖췄는지 판정한다.
3. 후보를 `admit`, `reinforce`, `route`, `reject` 중 하나로 분류한다.
4. 회사 내부 지식은 nbrain으로, 실행 절차는 skill이나 저장소 문서로, 행동 규칙은 AGENTS.md로 보낸다.
5. 저장하거나 보강할 후보와 제외한 후보의 이유를 함께 미리보기로 보여준다.
6. 사용자가 승인한 `admit`과 `reinforce` 후보가 있을 때만 소스를 해당 네임스페이스의 `raw/`에 보존한다.
7. 기존 wiki를 검색해 새 페이지 생성과 기존 페이지 보강을 결정한다.
8. wiki 문서에 메타데이터와 출처를 기록하고 양방향 링크를 연결한다.
9. INDEX와 log를 갱신한 뒤 qmd 인덱스를 갱신한다.
10. 미래 질문으로 검색해 대상 문서가 상위 결과에 나오는지 확인한다.

승인할 후보가 없으면 raw, wiki, INDEX, log, qmd 상태를 바꾸지 않는다.
회사 내부 내용이 섞인 소스는 개인 brain에 원문째 저장하지 않는다.
개인 지식만 독립적으로 분리할 수 있고 사용자가 확인한 경우에만 정제한 새 소스로 다시 판정한다.
같은 의미의 문서가 있으면 새 페이지를 만들지 않고 새로운 사실이나 근거가 있을 때만 보강한다.
출처 신뢰도를 판단할 수 없으면 `verified: false`로 미리보기에 표시하고 사용자 결정 전에는 저장하지 않는다.

## 에이전트 검색 흐름

1. 질문에서 대상 네임스페이스를 결정한다.
2. public은 `brain-wiki`, private은 `brain-private` 컬렉션으로 각각 검색한다.
3. 각 네임스페이스의 상위 후보를 읽고 질문과 직접 관련된 근거를 고른다.
4. 후보 문서의 관련 개념 링크를 한 단계 따라가 누락된 전제와 반례를 찾는다.
5. 답변이 부족할 때만 해당 네임스페이스의 raw 원문으로 내려간다.
6. 답변에 네임스페이스와 문서 경로를 붙이고, brain 밖 지식은 분리해 밝힌다.

검색 transport가 설정되면 HTTP qmd를 우선하고, 실패하면 로컬 고정 qmd와 INDEX·`rg` 순서로 축소한다.
실제 service 주소, mount와 갱신 절차는 private 인프라 저장소에서 관리한다.

## 사람의 탐색 흐름

1. Quartz 홈의 Memory Atlas에서 전체 노드와 연결 수를 확인한다.
2. 기본 2D 전체 지도에서 가까이 모인 지식 영역과 커리어, 건강, AI 시작점을 확인한다.
3. 고정 시작점이나 자동으로 발견한 영역을 선택하면 2D 지역 관계로 이동한다.
4. 노드를 직접 선택해도 같은 지역 관계로 전환하며, 선택 노드를 중앙에 두고 실제 wiki 연결을 hop depth별로 다시 배치한다.
5. 지역 관계에서 연결 노드를 선택하면 해당 노드를 새 중심으로 관계와 depth를 다시 계산한다.
6. 전체 지도로 돌아가기를 선택하거나 선택을 해제하면 처음의 결정적 2D 배치를 복원한다.
7. 3D 조망을 선택하면 현재 필터와 선택 노드를 유지한 채 별자리로 전환한다.
8. 제목 검색이나 유형, 태그, 최신성, 네임스페이스 필터로 후보를 좁힌다.
9. 노드 상세에서 설명, 상태, 수정일, 태그, 들어오고 나가는 연결 수를 확인한다.
10. 원문 열기를 선택하면 같은 어두운 항해도 셸의 문서 화면으로 이동한다.
11. 문서 화면에서는 제목 아래의 신뢰 메타데이터와 읽을 수 있는 로컬 그래프, 백링크로 근거와 인접 관계를 읽는다.
12. 항해도로 돌아가기를 선택하면 이전 필터, 선택 노드, 2D 또는 3D 모드와 조망 위치를 복원한다.

메타데이터가 없는 항목은 표시하지 않되 페이지 자체는 정상 렌더한다.
`stale_after` 날짜가 되었거나 지났으면 최신성 경고를 보여준다.
날짜가 잘못되었으면 날짜 대신 경고 상태만 표시한다.

Memory Atlas는 콘텐츠 색인과 정제된 의미 관계 산출물을 한 번 읽고 브라우저 안에서 필터, 혼합 관계와 배치를 계산한다.
의미 관계 산출물이 없거나 현재 빌드의 slug와 맞지 않으면 wiki 연결과 태그만 사용하고 탐색 상태에 축소 동작을 알린다.
필터 결과가 없으면 조건을 초기화하는 동작과 함께 빈 상태를 보여준다.
콘텐츠 색인을 읽지 못하면 오류 원인과 다시 시도 동작을 보여주고, 서버가 만든 문서 목록을 탐색 경로로 유지한다.
현재 모드의 렌더러만 초기화하지 못하면 다른 모드와 문서 목록은 계속 사용할 수 있게 한다.
SPA 이동이나 필터 재적용이 겹치면 이전 렌더러와 애니메이션을 먼저 정리하고 마지막 상태만 화면에 남긴다.

모바일에서는 그래프가 화면을 채우고 모드 전환, 작은 필터 버튼과 검색 막대만 그래프 위에 둔다.
필터는 왼쪽 서랍, 노드 상세는 아래 시트로 연다.
`Escape`는 질문 패널, 검색, 상세 시트와 필터 서랍을 닫은 뒤 선택을 해제한다.
검색, 모드와 모든 토글은 실제 HTML 입력 또는 버튼 요소를 사용한다.
사용자가 움직임 줄이기를 선택했으면 자동 회전과 장식 애니메이션을 사용하지 않는다.

외부 인증 계층은 비공개 그래프 진입 전에 인증을 끝낸다.
Memory Atlas는 별도 권한 API를 호출하지 않으며, 현재 빌드의 콘텐츠 색인에 포함된 네임스페이스만 보여준다.
public 빌드에는 private 노드가 없고 private 필터도 표시하지 않는다.

## Memory Atlas 의미 관계 생성 흐름

1. 생성기는 명시적으로 받은 wiki root와 qmd collection의 대응만 읽는다.
2. 각 문서의 제목, 설명과 태그를 qmd 내부 HTTP `/query`의 `vec` 검색어로 보낸다.
3. 결과에서 허용 collection의 wiki 문서만 받고 source와 target slug, 점수만 임시 산출물에 기록한다.
4. 같은 undirected slug 쌍은 가장 높은 점수 하나로 합치고 self-link와 임계값 아래 결과를 제외한다.
5. 생성이 실패하면 이전 임시 산출물을 삭제해 오래된 의미 관계를 다음 빌드가 사용하지 못하게 한다.
6. Quartz emitter는 현재 빌드의 콘텐츠 slug가 양쪽에 있는 관계만 남겨 정적 의미 관계 파일을 만든다.
7. 브라우저는 정제된 의미 관계를 wiki 연결과 공통 태그 관계에 합쳐 전체 2D 지도와 자동 시작점을 계산한다.

public 생성은 `brain-wiki`만 입력으로 받는다.
private 포함 생성은 `brain-wiki`와 `brain-private`를 사용할 수 있지만, public 빌드의 emitter는 현재 콘텐츠에 없는 private slug를 모두 제외한다.
임시 산출물에는 제목, 태그, 문서 본문, qmd 발췌문과 자동 군집 이름을 기록하지 않는다.

## Brain 근거 질문 흐름

1. 사용자가 Memory Atlas의 `Brain에게 묻기`를 열고 500자 이하 질문을 보낸다.
2. 같은 출처의 웹 계층이 `POST /api/brain/ask`를 질문 BFF로 전달한다.
3. `brain-ask`는 동시에 처리 중인 요청이 있는지 확인하고, 있으면 `busy`로 끝낸다.
4. 질문 BFF가 내부 qmd transport에 같은 질문의 키워드·벡터 검색을 요청한다.
5. 검색 결과에서 `brain-wiki`와 `brain-private`만 받아 최대 6개 문서를 고른다.
6. qmd URI를 허용된 읽기 전용 wiki 경로로 바꾸고, 각 문서와 전체 근거 크기를 제한해 본문을 읽는다.
7. 근거가 없으면 모델 API를 호출하지 않고 빈 근거 응답을 반환한다.
8. 근거가 있으면 전용 모델 API의 `/v1/responses`에 질문과 근거를 전달한다.
9. 모델은 도구 없이 근거 안에서만 평문 답변을 만들고 대화를 저장하지 않는다.
10. 질문 BFF가 답변과 결정적으로 만든 출처 목록을 반환한다.
11. Memory Atlas는 답변을 평문으로 보여주고 패널이 열려 있는 동안 출처 노드를 강조한다.
12. 사용자가 패널을 닫으면 질문, 답변과 출처 강조를 모두 브라우저 메모리에서 지운다.

qmd 호출은 10초, 모델 API 호출은 90초 안에 끝나야 한다.
qmd 장애, 모델 장애, 모델 시간 초과와 동시 요청은 서로 다른 오류 상태로 보여주며 다시 시도할 수 있다.
서버 로그에는 요청 식별자, 성공 여부, 단계별 시간과 근거 개수만 남긴다.
질문, 답변, 발췌문과 사용자 이메일은 기록하지 않는다.

## 운영 구성 경계

public 저장소는 질문 API와 UI의 일반 계약만 검증한다.
모델 profile, container 연결, reverse proxy와 실제 게시·rollback 흐름은 private 인프라 저장소가 소유한다.

## OKF 내보내기 흐름

1. 명령이 public `wiki/`와 `raw/`만 읽는다.
2. concept, topic, entity 문서의 제목과 첫 설명 문단으로 누락된 교환용 메타데이터를 보완한다.
3. raw Markdown 사본에는 누락된 `type: Reference`만 추가하고 원본 본문과 wikilink는 보존한다.
4. Markdown 이외 raw 파일은 내용 변경 없이 복사한다.
5. 내부 `wiki/INDEX.md`는 `wiki/index.md`로 내보내고 `wiki/log.md`와 함께 예약 문서로 보존한다.
6. wiki의 bare-slug 링크를 내보내기 묶음 안의 상대 Markdown 링크로 바꾼다.
7. 묶음 루트에 `okf_version`만 frontmatter로 가진 `index.md`를 만든다.
8. 해석할 수 없는 wiki 링크가 있으면 성공으로 숨기지 않고 오류로 보고한다.

출력 경로가 이미 존재하면 명시적인 덮어쓰기 선택 없이는 중단한다.

## 배포 검증 책임

public 저장소는 unit test, Quartz build와 브라우저 회귀를 제공한다.
private 인프라 저장소는 이 결과물을 실제 서비스에 게시하고 접근 제어, rollback과 색인 갱신을 검증한다.
